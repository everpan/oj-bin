> 审查对象：`only-js`（oj）工作区 —— 嵌入 deno_core/V8 的低代码后端框架。
> 审查方式：通读核心运行时、FFI/ABI 层、安全关键路径（SQL 注入防御、路由守卫、鉴权、证书门禁）、

## 值得肯定的设计

- **SQL 注入根治**：`SchemaRegistry` 白名单（标识符）+ 绑定参数（值）双层防御，且为「拒绝式」
  （未知表/列直接 400），而非「匹配式」兜底。全仓最硬的安全资产。
- **`!Send` JsRuntime 隔离模型**：`JsActor` 把 Bridge 钉在 OS 线程 + channel 通信，axum 侧只持
  Send 的 handle，future 天然 Send。`KillSwitch` 用 `IsolateHandle`（而非裸指针）跨线程 terminate，
  以及 EDEADLK 自 join 修复（`src/bridge/runtime.rs:174`）——是踩坑后才有深度。
- **Plugin ABI 设计**：`oj-plugin-ffi` 共享契约 + `stabby` 让 repr(C) 跨边界可转 + `oj_plugin_entry!`
  内建 `catch_unwind` + 二级 ABI 门禁（函数符号 + descriptor 字段）。`FfiFuture` 的
  poll/take/free 三态协议把 panic 收敛为错误 future，而非跨界 UB。
- **路由表**：`FileId` 去重、`.route` 替换语义（dev 兜底不复活）、`decode_params` 的 `%2F`
  走私校验——边角都想过。

## 建议改进项（按优先级）

### P1 — `fetch` 无访问控制（SSRF）【状态：成立，方案已定，待做】

`bootstrap.js` 的 `fetch` 把任意 URL 透传给 `op_fetch`，无 scheme/域名白名单。JS handler 是受执行的
代码，可打到云元数据端点（`169.254.169.254`）、内网服务、`file://` 等。全仓看不到任何 SSRF 防护。
若 `fetch` 会暴露给外部租户 handler，这是最该补的一点。建议至少：默认拒绝
`file://`/`http://127.0.0.1`/私网段，或提供 `fetch` allowlist 配置项。

> **复核**：成立。`src/bridge/fetch.rs:35` 任意 URL 直通 `client.request`，无任何校验；
> reqwest 0.13（rustls）的 `dns_resolver` API 可用。
> **方案**：自定义 `reqwest::dns::Resolve`，在**解析层**过滤私网/环回/链路本地 IP——
> 天然覆盖重定向每一跳与 DNS rebinding；reqwest 对非 http(s) scheme 本就报错，`file://` 无需单独处理。
> `ServerCfg` 加 `fetch_private: bool`（默认 `true` 保住本地 dev 与现有测试），
> StableState 带开关、client 构建时挂 resolver，fetch.rs 约 40 行 + deny/allow 各一条测试。
> **不默认 deny**：默认收紧会砸掉调 localhost 内部服务的现有 handler；默认放开 + 配置收紧是兼容渐变路径。

### P1 — 同步阻塞 DNS 解析落在 async 上下文【状态：复核不成立，不修】

`oj/src/server_cmd.rs` 多处调 `to_socket_addrs_sync` 做地址解析。高并发或 DNS 慢时会阻塞 async
runtime。小改进：改用 `tokio::net::to_socket_addrs` 的异步版本，或放在 blocking 任务里。

> **复核**：不成立。`to_socket_addrs_sync` 仅在 `run()`/`start()` 启动期各调一次
> （`server_cmd.rs:134` 注释自证「仅启动调用一次」），此刻尚无并发流量，host 通常为数字地址。
> 「高并发阻塞」不成立，改异步是无效 churn。

### P2 — 归属守卫的表名提取是 best-effort lexer，deny 模式「漏抓=放行」【状态：成立，定性后修】

`src/bridge/guard.rs` 的 `extract_tables` 是词法扫描（FROM/JOIN/INTO/UPDATE 后取词），不是解析器。
`ownership_deny=true` 时，`judge()` 对 `owner=None` 的表直接放行（`guard.rs:113`），而 lexer 漏掉的
表（CTE `WITH x AS (...)`、`FROM (subquery)`、`VALUES` 子句、反引号/别名等）会静默放行。

deny 模式的强度完全取决于这个 lexer 的完备性。现实建议三选一：
1. deny 模式仅在建构器路径（`db.table()`）生效，裸 SQL 一律 warn；
2. 引入轻量 SQL 解析器（如 `sqlparser-rs`）做表名提取；
3. 明确文档化：deny 模式要求所有访问走 `db.table()`，裸 SQL 不受 deny 约束。

> **复核**：成立，但缺口面比原文小——CTE/子查询里的 `FROM t` 仍被第二个 FROM 抓到
> （词序扫描特性），真实缺口是 `TRUNCATE TABLE t`、`TABLE t` 等关键字外语句。
> `owner=None` 放行是 `guard.rs` 注释明示的既定语义（交给静态 S003）。
> **方案分两层**：
> - 定位为模块纪律 lint（现状）：补 `TRUNCATE`/`TABLE` 进关键字表（`guard.rs:88`）+ 文档明示
>   deny 为 best-effort，成本 ≈ 0；
> - 定位为硬安全边界（对外承诺）：引 `sqlparser-rs` 替换 `extract_tables`，且 **parse 失败时
>   deny 模式拒绝（fail-closed）**——才真正封死「漏抓=放行」。
> 建议：现在走第一层；deny 模式要写进安全承诺时再上第二层。

### P3 — `to_qv` 大浮点截断为 f32【状态：已修复（bb48576）】

`src/bridge/query.rs:97` `Qv::Float(Some(f as f32))` —— `f64 → f32` 截断会让大数/高精度小数丢失
精度（金额、时间戳）。sea-query 有 `Qv::Double`，对 float 列用 `Double` 更准。

> **复核**：成立，且下游全兼容——`bind_value` 本就绑 f64（`accessor_sqlx.rs:60`），
> `value_to_json` 已处理 `Qv::Double`（`query.rs:267`）。
> **已修复**：`Qv::Float(Some(f as f32))` → `Qv::Double(Some(f))`，一行（bb48576）。

### P3 — `bind_value` 的 `other` 分支跨方言隐患【状态：部分成立，文档化，不修】

`src/bridge/accessor_sqlx.rs:66` `other => q.bind(other.to_string())` 把对象/数组序列化成字符串
绑定。SQLite 无所谓，但 Postgres 的 `jsonb`/`json` 列会收到字符串而非 JSON 值，语义不符。
`column_json`（`:109`）对字节列同样 `from_utf8_lossy`，二进制数据会失真。

> **复核**：部分成立。真修需过三方言 × Any 驱动的 json/blob 绑定矩阵，且 bytes→base64 会破坏
> 现有输出形态（含已测行为 `select ? as v` 字符串化）。workaround 已存在：handler 传串、
> 二进制走 blob 轴。**处置**：在 api-manual 限制章节补文档，不动代码。

### P3 — `handle()` 与 `run` 闭包是超长单体【状态：复核不成立，不修】

`server/src/lib.rs` 的 `handle` 约 416 行，把证书检查、auth 路由、blob 路由、租户、multipart、
鉴权、静态站点全塞在一个 cascade 里；`run` 闭包也近 70 行。功能正确，但可读性/维护成本高。建议把
auth/blob/tenant 三段抽取为独立 `Step`/中间件，`handle` 只做编排。

> **复核**：不成立。实际为 `server/src/lib.rs:226-416` ≈ 190 行（原文误读），且是**顺序敏感的
> 早退 cascade**（cert → auth → blob → 路由表 → dev 兜底 → 静态，顺序即语义），
> 拆中间件反而把隐式顺序变显式配置。现状即最简正确形式。

### P3 — `DELIVER_TARGETS` 进程级全局可变状态【状态：挂起，记录升级路径】

`src/bridge/ffi.rs:488-503` 的 `DELIVER_TARGETS` 是 `static` 全局表，被 `host_deliver`（原始 C
回调）和 `FfiEventBroker` 并发读写。跨 bridge/跨 broker 共享 fan-out 语义依赖它，测试也因此要
串行化（`T_LOCK`）。这是可测试性与正确性隐患——多个 bus broker 的订阅汇同一张表，靠 `same_channel`
去重。考虑把 delivery 目标收进 `StableState` 或按 broker 隔离。

> **复核**：成立但根因是 FFI `deliver` 回调签名无 ctx 指针（`ffi.rs:486` 注释），
> 收进 StableState/broker 需 ABI v5→v6。Mutex 已保证正确性、M-1 已按归属清理。
> **处置**：挂起；在 ffi.rs 注释记录「多 broker 隔离需 ABI bump」即可。

### P4 — 几处小问题【状态：见各项】

- `src/bridge/mod.rs:300-302` `reqwest::Client::builder()...unwrap_or_default()` —— builder
  失败被静默吞掉。builder 失败通常意味着底层 ssl 后端缺，值得 fail-fast。

  > **已修复（bb48576）**：`unwrap_or_default()` 的 fallback 本身是假的
  > （`Client::default()` 内部同样 panic），改为 `.expect("build reqwest client")` 显式 fail-fast。

- `server/src/auth.rs:124-132` `is_anonymous` 的 `/*` 前缀通配实际匹配**任意深度**
  （`starts_with(prefix)` 对 `/pub/sub/x` 也成立），与注释「一层前缀通配」不符。

  > **复核**：任意深度是更常规的前缀通配语义，行为不改；**建议改注释**对齐实现，尚未做。

- `server/src/auth.rs:171-191` refresh 轮换 get→del 非原子（已文档化低危），并发两次 refresh 会
  签出两枚新 token 并存。真要堵需 KV 原子操。

  > **不修**：代码已有 `auth.rs:169` ponytail 注释明示低危、v0.2 不做，与复核一致。

- `server/src/routes.rs` 的 mixed-segment pattern 拒绝行为是按 pinned 的 matchit 0.8.4 版本定的
  （`:740` 测试注释），依赖版本锁定行为——后续升级 matchit 需回查。

  > **不修**：`:740` 测试注释已记录「0.8.6 放宽后此测试需反转」，回查义务已落档。

## 待确认的设计点

**证书门禁只对 GET 生效**（`server/src/lib.rs:236`），非 GET 即便证书过期/宽限仍走到路由层。这是
有意的（测试 `non_get_allowed_when_cert_expired` 显式断言），但意味着过期后 POST/PUT/DELETE 仍可写。
确认是否接受该语义——多数「证书门禁」场景下写入同样需要证书校验，只限读可能不够。

> **复核**：语义反直觉——通常门禁应先限写（宽限期内「可写不可读」说不通）。
> 两个选项：接受现状并文档写明；或门禁扩到全部方法（`/health` 除外）、测试同步反转。
> 无更多背景倾向后者（证书失效默认收敛攻击面更稳），**待产品拍板**。
